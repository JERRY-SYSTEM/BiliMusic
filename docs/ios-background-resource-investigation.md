# iOS 长时间后台播放资源排查

## 结论与证据

代码检查发现资源保留和无界增长风险，但没有 iOS 崩溃日志、内存曲线或文件句柄统计，不能确认六个症状均由内存泄漏造成，也不能确认搜索闪退属于 Jetsam。

- `audio_player_handler.dart` 的 `_prefetchNext` 持续追加音频源，自动切歌不会移除已播放项。大型列表顺序播放时，原生队列随已播放歌曲数增长，直到重建才释放旧源。
- `player_queue_manager.dart` 的随机播放历史没有上限；歌词封面查询缓存原来永久保留 Future，失败结果也保留。
- 图片、歌词、搜索及其 WBI/指纹依赖只设连接超时，响应头或响应体不结束时，请求仍可能长期占用资源。
- 音频下载的 `IOSink.add` 不等待磁盘写入，快速下载与慢速存储组合可能积压内存缓冲。
- 缓存统计对每个封面文件重复遍历歌曲和尺寸并计算哈希，开销随文件数与歌曲数的乘积增长。这是加载卡顿问题，不等同于泄漏。

## 修改

- 原生预取队列最多保留 3 项；窗口末尾仍提前下载下一首，播放结束后复用已有重建逻辑释放旧队列。随机播放保留最近 200 次历史。
- 短请求最多并发 8 个；等待名额和网络操作各有 20 秒超时，结束或超时关闭该请求独占的客户端。音频下载不共用这些名额。
- 歌词封面只合并正在进行的请求，完成后移除，允许失败重试；可选封面解析失败不丢弃整组搜索结果。
- 应用封面解码边长限制为 1080；系统媒体封面配置缩放到 512×512；前台恢复时重试网络加载失败的图片。
- 音频每约 64 KiB 等待磁盘写入，限制写缓冲积压。
- 封面归属哈希先建立索引，再逐个扫描缓存文件，避免重复计算。

`audio_service` 的封面缩放配置说明见[上游源码](https://github.com/ryanheise/audio_service/blob/master/audio_service/lib/audio_service.dart)。

## 验证状态与限制

本次环境为 Windows，未找到 Flutter/Dart SDK；只完成代码审阅和 `git diff --check`，未运行 Dart 分析、测试或 iOS 构建。新增测试覆盖 30 首自动播放的队列上限与顺序，以及响应头/体卡住、并发名额超时和请求失败后的恢复。

在具备 Flutter SDK 的环境执行：

```sh
flutter pub get
flutter analyze
flutter test test/bili_http_test.dart test/audio_player_handler_test.dart test/player_queue_manager_test.dart
flutter test
```

原生窗口重建边界可能出现短暂停顿，因此该策略不保证每首之间始终无缝；需实机检查这一行为。完整逻辑播放列表不受 3 项限制，上一首和任意跳转仍走现有导航逻辑。

## iOS 实机复测

使用 Profile 构建，在相同设备和播放列表上对比修改前后：

1. 顺序后台播放至少 30 首并覆盖原问题出现的时长，另测随机与单曲循环。
2. 观察 Instruments 的内存和文件资源是否持续增长；窗口重建后是否回落。
3. 播放期间断网、恢复网络、多次锁屏与解锁，然后检查控制中心封面、主页图片、缓存管理、搜索框和歌词搜索。
4. 若仍闪退，收集设备对应时间的崩溃报告及 Jetsam 日志，区分内存杀进程、原生异常、文件句柄耗尽和 UI 卡死。

自动测试的假播放器无法证明 AVFoundation 已释放资源；必须以实机结果确认。
